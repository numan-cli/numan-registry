# 2026-11-11 provisional package re-proof

Scope: the three versions left `evidence_tier: provisional` by the
2026-11-11 lifecycle triage.

## Final resolution

All three versions are now terminal, not provisional-open. Each version entry
carries an optional `yanked` object with a stable `reason_code` and an
`evidence_url` pointing at this document. Presence of `yanked` means the
version must not be installed or activated; the failed proof records and the
original artifact hashes are preserved. No `verified_with` value remains on these
terminal entries: the probes below failed, so presenting any of them as a passing
verification would be false.

| Package | Version | Declared Nu | Terminal status | Reason code |
|---|---|---|---|---|
| `Trivernis/nu-plugin-dialog` | 0.1.0 | `>=0.78.0 <0.79.0` | yanked | `nu-plugin-protocol-mismatch` |
| `amtoine/nu-git-manager` | 0.8.0 | `>=0.92.0` | yanked | `nu-parser-incompatible` |
| `amtoine/nu-git-manager-sugar` | 0.7.0 | `>=0.92.0` | yanked | `nu-parser-incompatible` |

The dialog entry originally claimed `>=0.107.0 <0.108.0`. The released
artifact was built against `nu-plugin 0.78.0`, so the index now declares the
actual protocol era (`>=0.78.0 <0.79.0`) and marks the version yanked. It is
not presented as installable on a Numan-supported Nu; the `yanked` marker
supersedes the compatibility range for availability decisions.

`evidence_tier: provisional` and the existing `deferral_reason` remain as the
historical evidence classification. They are not the terminal availability
signal; consumers must check `yanked` first.

## Dialog protocol diagnosis

The upstream `v0.1.0` manifest pins:

```toml
nu-plugin = "0.78.0"
nu-protocol = "0.78.0"
```

Source: <https://github.com/Trivernis/nu-plugin-dialog/blob/v0.1.0/Cargo.toml>

The indexed Nu range (`>=0.107.0 <0.108.0`) was therefore incompatible with
the released binary. On Nu 0.107.0 the lifecycle failed at activation with:

```text
nu::shell::plugin_failed_to_decode
Plugin failed to decode: unknown variant `Error`
```

Nu 0.78.0 is the protocol-era host, but Numan 0.4.0 cannot drive it: the
isolated Nu probe fails because `$nu.data-dir` does not exist. A valid dialog
proof requires an upstream rebuild against a supported Nu (and a new artifact
hash), or a Numan change that supports the old Nu path model. Until then the
version is yanked and cannot be installed.

## Module diagnosis

Both archived modules are platform-independent archives. The same activation
errors reproduce across Nu versions:

| Package | Nu tested | Failure |
|---|---|---|
| `amtoine/nu-git-manager` | 0.113.1, 0.107.0, 0.105.0 | `nu::parser::operator_incompatible_types` at `mod.nu:139` |
| `amtoine/nu-git-manager-sugar` | 0.113.1, 0.107.0 | `nu::parser::extra_positional` at `git/mod.nu:347` |
| `amtoine/nu-git-manager-sugar` | 0.105.0 | `nu::parser::parse_mismatch` at `github.nu:144` |

Nu 0.101.0, 0.92.0, and 0.78.0 cannot complete Numan's module preflight because
the isolated vendor-autoload target is unavailable. The module parser failures
begin at the earliest Numan-compatible Nu tested, so there is no overlap between
a supported Numan host and a parser that accepts these archived payloads. Both
upstreams are archived and no maintained public fork or successor was found in the sources checked;
the maintained alternative is `fj0r/git.nu`.

## Commands

The probes used the current Numan 0.4.0 debug binary and the committed candidate
index, with each Nu archive placed in a disposable directory:

```text
lifecycle-prove --package Trivernis/nu-plugin-dialog --package-version 0.1.0 \
  --candidate-index <temporary-index-with-0.78-range> --numan <numan> --nu <nu-0.78.0>

lifecycle-prove --package amtoine/nu-git-manager --package-version 0.8.0 \
  --candidate-index registry/index.json --numan <numan> --nu <nu-0.105.0>

lifecycle-prove --package amtoine/nu-git-manager-sugar --package-version 0.7.0 \
  --candidate-index registry/index.json --numan <numan> --nu <nu-0.105.0>
```

Nu archives with published `SHA256SUMS` were checksum-verified. The 0.78.0 and
0.92.0 releases have no `SHA256SUMS` asset at their GitHub release tags; those
binaries were used only for preflight diagnosis, not as production proof
evidence.

## Metadata and consumer behavior

- Schema: `schemas/index-v1.json` adds an optional version-level `yanked`
  object with required `reason_code` and `evidence_url`. The change is additive
  and optional, so no `schema_version` bump is required; entries without
  `yanked` keep their previous shape and canonical bytes.
- Client: this registry PR defines the schema and catalog contract. The
  companion client change is separate and is not part of this diff; until it
  ships, production filtering protects older clients.
- Production: `scripts/materialize_candidate.py` drops versions marked
  `yanked` (as well as provisional versions), so older clients that ignore the
  new field never receive these entries from the production catalog.

No proof was rerun. No artifact was rebuilt, re-hashed, or re-signed. The
artifact hashes in the index and the detached signature envelope are unchanged;
this is a metadata-only correction.

## Remaining decisions

`Trivernis/nu-plugin-dialog@0.1.0` is effectively withdrawn. Restoring it
requires an upstream rebuild for a supported Nu, or a separate Numan
compatibility project for the 0.78 path model. The two archived `amtoine`
modules are likewise deprecated and withdrawn; using `fj0r/git.nu` is the maintained
alternative. No further registry-side action is needed unless upstream
publishes replacement artifacts. The stale `[watch]` issue
[#109](https://github.com/numan-cli/numan-registry/issues/109) was closed as
not planned on 2026-11-12 after this decision was recorded.
